1. Overview

Once a day, the script checks a list of contractor accounts in your organization and sends an email warning if any of those accounts are about to expire. It looks 14 days ahead by default. If nothing is expiring, no email is sent.

Why it exists

Contractor accounts in your organization's user directory (called Active Directory) expire on a set date. If no one notices in time, the contractor loses access to systems and work stops. This script gives advance warning so the account can be renewed before that happens.

How it works

The script runs automatically on a schedule. It reads from a group called Contractors in your organization's directory, finds any accounts expiring within the next 14 days, and sends one summary email to the addresses you configure. If no accounts are expiring soon, it quietly finishes without sending anything.

2. Requirements

Before the script can be used, the following must be in place:

  • A Windows server or computer that is connected to the company network and can access the organization's user directory (Active Directory). This is typically any domain-joined Windows server.
  • PowerShell — included with Windows; no separate installation needed.
  • RSAT (Remote Server Administration Tools) — a free Windows add-on that lets PowerShell read user account information. Your IT administrator can install this. On Windows Server, it is usually already available.
  • A Microsoft 365 shared mailbox for the script to send email from. A shared mailbox does not require a license. Ask your IT administrator if you do not already have one set up.
  • A security permission set up in Microsoft's cloud portal — this tells Microsoft 365 that the script is allowed to send email on behalf of your organization. This is a one-time step covered in the next section. An administrator account is required.

3. Setting Up the Security Permission (App Registration)

Before the script can send email, it needs a permission slip from Microsoft. This is called an App Registration. Think of it as registering the script as a trusted application that is allowed to send email through your organization's Microsoft 365 account. This only needs to be done once.

You will need an administrator account to complete these steps. If you do not have one, ask your IT administrator to do this part for you — they will need to give you three values at the end: Tenant ID, Client ID, and the security credential.

Step-by-step instructions

  1. Sign in to Microsoft's cloud portal at entra.microsoft.com using an administrator account.
  2. In the left navigation, click App registrations, then click New registration.
  3. Give the app any name — for example, Contractor Expiration Alert. Leave all other settings at their defaults and click Register.
  4. You will land on the app's Overview page. Copy and save two values from this page:
    • Application (client) ID
    • Directory (tenant) ID
  5. Click API permissions in the left navigation. Click Add a permission, choose Microsoft Graph, then choose Application permissions.
  6. In the search box, type Mail.Send. Check the box next to Mail.Send and click Add permissions.
  7. Click Grant admin consent for [your organization] and confirm. The status column next to Mail.Send should change to a green checkmark.
  8. Click Certificates & secrets in the left navigation. Click New client secret. Give it any description, choose an expiration of 24 months, and click Add.
  9. Important: Copy the secret's Value immediately — it is only displayed once. Note the expiration date somewhere safe (a calendar reminder 30 days before it expires is recommended).

You now have the three values needed for first-time setup: Tenant ID, Client ID, and the security credential. Keep these in a secure place.

What is the security credential? Think of it like a password for the script. It proves to Microsoft that the script has permission to send email on behalf of your organization. It expires after the period you chose (typically 24 months) and must be renewed — see Section 8 — Renewing the Security Credential for instructions.

4. The Contractors Security Group

In your organization's user directory (Active Directory), there is a group called Contractors. The script monitors every account that is a member of this group — and only those accounts. It does not look at every user in the organization.

What this means for you

  • If a contractor account is not in the Contractors group, the script will not warn about it — even if it is about to expire.
  • If a contractor account is in the group but has no expiration date set, the script flags it in a separate section of the email as a potential oversight. Every contractor account should have an expiration date.
  • Accounts that are disabled are ignored — the script only checks active accounts.

Managing group membership

Group membership is managed by your IT administrator. If a contractor should be receiving expiration warnings but is not appearing in the alert emails, ask IT to:

  1. Add the contractor's account to the Contractors group in Active Directory.
  2. Make sure an expiration date is set on that account.

5. Script Options

The script accepts several options that control how it behaves. The two required ones must be provided every time the script runs (they are included in the scheduled task command). All others are optional.

Option What it does Required? Default
-GroupName The name of the security group to monitor. This must match exactly what is in Active Directory. Yes —
-To Who receives the alert email. You can list more than one address, separated by commas. Yes —
-Cc Additional people who receive a copy of the email. Optional. No None
-WarnDays How many days ahead to look for expiring accounts. No 14
-Setup Runs the first-time setup wizard. Also used when updating the security credential after it expires. No Off
-ReportOnly Preview mode — shows what the email would say without actually sending it. Useful for testing. No Off
-Diagnostics Prints extra detail to the screen while running. Useful when troubleshooting a problem. No Off
-LogHistory How many days of log files to keep before they are automatically deleted. No 30
-SkipUpdateCheck Skips checking online for a newer version of the script at startup. No Off

6. First-Time Setup

Before the script can send email, you need to run a one-time setup. This stores the Microsoft 365 connection details securely on the computer where the script will run.

Before you begin: Complete Section 3 (Setting Up the Security Permission) first and have your Tenant ID, Client ID, and security credential ready.

Setup walkthrough

  1. Open PowerShell on the server where the script is installed. Important: if you are setting this up for a scheduled task, open PowerShell as the service account that will run the task — see the note below and Section 7.
  2. Navigate to the folder where the script is saved. For example, if the script is in C:\Scripts\contractor-expiration-alert, type cd C:\Scripts\contractor-expiration-alert and press Enter.
  3. Run the setup command, replacing the email address with your actual recipient:

    .\Send-ContractorExpirationAlert.ps1 -GroupName 'Contractors' -To 'alerts@yourcompany.com' -Setup
  4. The script will display a checklist of prerequisites. Press Enter to continue.
  5. When prompted for Tenant ID, paste the value you copied from the portal and press Enter.
  6. When prompted for Client ID, paste the value and press Enter.
  7. When prompted for the Security Credential, paste the value and press Enter. The cursor will not move while you type or paste — this is normal. The value is hidden for security.
  8. When prompted for the From address, type the shared mailbox address the script will send email from and press Enter.
  9. The script will test the values against Microsoft's servers. If everything is correct, it saves the configuration and displays a success message. If there is an error, it will describe what went wrong — double-check that the values were copied correctly and that admin consent was granted (Step 7 in Section 3).

Why does the account used for setup matter? The configuration file is protected by Windows and can only be read by the same Windows account that created it. If the scheduled task runs as a different account than the one that ran setup, the script will not find its configuration and will not run. When in doubt, re-run setup while using the service account (see Section 7).

7. Scheduled Task

The script is meant to run automatically every day so that no one has to remember to run it manually.

How the task works

  • The task runs daily at a configured time (for example, 10:00 AM).
  • It runs as a specific Windows service account — a user account created just for this purpose.
  • That service account must have been used to run -Setup first. Without this, the script cannot find its configuration and will not run. See Section 6.
  • A log file is saved automatically in the logs folder inside the script's directory after each run. Log files are named by date and time (for example, ContractorExpirationAlert_2026-05-07_100001.txt). Logs older than 30 days are deleted automatically.

Checking that the task is running

  1. Open Task Scheduler (search for it in the Start menu).
  2. Find the task named Contractor Expiration Alert.
  3. Look at the Last Run Time and Last Run Result columns:
    • A result of 0x0 means the task completed successfully.
    • Any other value indicates a problem — open the most recent log file in the logs folder to see what went wrong.

If the task stops running after a server restart or Windows Update

Occasionally, Windows Updates or server restarts can disable scheduled tasks. Open Task Scheduler, find the Contractor Expiration Alert task, and check that it is not disabled. If it is disabled, right-click it and choose Enable.

8. Renewing the Security Credential

The security credential (the "password" that allows the script to send email) has an expiration date — typically 24 months from when it was created. When it expires, the script will stop sending emails and log an error.

Recommended: Set a calendar reminder 30 days before the credential expires. You can find the expiration date in the portal under the app registration's Certificates & secrets page.

What to do when the credential expires

  1. Sign in to Microsoft's cloud portal at entra.microsoft.com using an administrator account.
  2. Go to App registrations and open the Contractor Expiration Alert app.
  3. Click Certificates & secrets in the left navigation.
  4. Click New client secret. Give it a description and choose a 24-month expiration. Click Add.
  5. Important: Copy the new secret's Value immediately — it is only shown once.
  6. Note the new expiration date and update your calendar reminder.
  7. On the server, open PowerShell as the service account (the same account used during first-time setup) and run:

    .\Send-ContractorExpirationAlert.ps1 -GroupName 'Contractors' -To 'alerts@yourcompany.com' -Setup
  8. When prompted, enter the same Tenant ID and Client ID as before. When prompted for the security credential, paste the new value.
  9. The script will test and save the new credential.

Do not delete the old credential in the portal until you have confirmed the new one works. Verify by checking that the next scheduled run completes with a Last Run Result of 0x0 in Task Scheduler.

9. Troubleshooting

If something does not seem to be working, use this table to find the cause and fix it.

What you see Likely cause What to do
No email received and no accounts are expiring soon The script is working correctly. It only sends email when there is something to report. Open the most recent log file in the logs folder and confirm the script ran. Look for a line that says "Nothing to report."
No email received but accounts should be expiring The script may not have run, or the contractor accounts are not in the Contractors group. Check Task Scheduler (Last Run Result should be 0x0). Ask IT to verify the accounts are in the Contractors group and have expiration dates set.
Log file shows "Failed to get access token" The security credential is wrong or has expired. Re-run the script with -Setup as the service account to update the credential. See Section 8 — Renewing the Security Credential.
Log file shows "No config file found for user" Setup was run under a different Windows account than the one the scheduled task uses. Re-run setup while using the service account. See Section 6 — First-Time Setup.
Log file shows the email failed to send (permission error) The app registration is missing the email-sending permission, or admin consent was not granted. Ask IT to verify the app registration in the portal — specifically that Mail.Send is listed under API permissions with a green consent checkmark. See Section 3 — Setting Up the Security Permission.
Log file shows it could not read the user directory The script cannot reach Active Directory, or the group name does not match exactly. Verify the server is connected to the company network. Ask IT to confirm the group name in Active Directory matches the name used in the scheduled task command.
The task stopped running after a Windows Update or server restart The scheduled task may have been disabled automatically. Open Task Scheduler, find the Contractor Expiration Alert task, and check that it is enabled. If not, right-click and choose Enable.

Checking log files

Log files are stored in the logs folder inside the script's directory. Each file is named with the date and time it was created (for example, ContractorExpirationAlert_2026-05-07_100001.txt). Open the most recent file in Notepad to see what happened during the last run.
